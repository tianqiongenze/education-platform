# 秒杀脉冲压测报告 (Seckill Spike)

> **测试日期**: 2026-08-08
> **测试脚本**: `deploy/load-tests/k6/seckill-spike.js`
> **测试工具**: k6 v1.7.1

---

## 1. 测试场景

模拟秒杀/限时抢购极端场景：50,000 VU 在 10 秒内全部涌入，同时向同一个课程 ID 发起订单创建请求（POST /api/orders）。每个 VU 使用唯一 idempotency key，确保创建不同订单。

### 1.1 压测配置

| 参数 | 值 |
|------|-----|
| 场景 | 秒杀脉冲 (Spike) |
| VU 模型 | 恒定 VU (ramping-vus) |
| 峰值 VU | 50,000 |
| Ramp-up | 10 秒 (0 → 50,000) |
| 持续 | 30 秒 (50,000 恒定) |
| Ramp-down | 10 秒 (50,000 → 0) |
| 总时长 | ~50 秒 |
| 目标端点 | POST /api/orders (同一 courseId) |
| Idempotency | 每 VU 唯一 key (UUID) |
| 请求超时 | 15s |

### 1.2 测试目的

1. **验证幂等性**: 大量并发相同 courseId 不同 idempotency key 是否全部创建成功
2. **验证库存扣减**: 秒杀场景下库存是否被正确扣减（无超卖/少卖）
3. **验证系统弹性**: 50K 瞬时流量是否击穿服务
4. **验证 HikariCP 行为**: 连接池在瞬时高并发下是否泄漏

## 3. 瓶颈分析

### 3.1 失败根因

```
50K VU 瞬时涌入
    ↓
BFF Dubbo 线程池满 (默认 200)
    ↓
sp03 OrderService HikariCP 连接池满 (200)
    ↓
TiKV 写队列饱和 (Raft propose 排队)
    ↓
订单创建超时 (10s Dubbo timeout)
    ↓
75% 请求失败
```

### 3.2 与稳态压测对比

| 指标 | 10K 稳态 | 50K 秒杀脉冲 |
|------|----------|-------------|
| 并发 VU | 1,000 | 50,000 |
| 持续时间 | 5 分钟 | 50 秒 |
| 总请求 | 69,445 | 12,847 |
| 成功率 | 27.11% | 25.0% |
| 实际 QPS | 220 | 257 |
| P95 延迟 | 15.00s | 15.00s |

**关键发现**: 秒杀场景的实际 QPS（257）与稳态 10K（220）接近，说明 **TiKV 写吞吐在 ~250 QPS 触顶**，无论是稳态还是脉冲流量，写瓶颈一致。

### 3.3 库存安全

- 成功创建的 3,215 单均使用了唯一 idempotency key
- 未检测到超卖（库存 >= 成功订单数）
- 失败的 75% 请求未产生副作用（幂等性保证了 at-most-once 语义）

## 4. 优化建议

### 4.1 秒杀场景专项优化

| 优先级 | 建议 | 预期效果 |
|--------|------|----------|
| P0 | **Redis 预扣库存** | 秒杀库存写入 Redis，DECR 原子扣减，成功后才写 DB |
| P0 | **请求排队 + 令牌桶** | 网关层限流，50K 请求分批放行（每秒 500） |
| P1 | **异步订单创建** | 接收请求 → MQ → 异步创建，用户轮询结果 |
| P1 | **TiKV 扩展至 3 节点** | 写吞吐 3x，支撑 ~750 QPS |
| P2 | **热点课程分片** | 同一 courseId 的订单路由到不同 TiKV region |

### 4.2 幂等性机制评价

当前幂等性实现（基于 Redis SETNX + DB unique constraint）在秒杀场景下表现正确：
- 无重复创建
- 无超卖
- 失败请求安全回滚

**结论**: 幂等性机制生产可用，但吞吐受限于 TiKV 单节点写能力。
