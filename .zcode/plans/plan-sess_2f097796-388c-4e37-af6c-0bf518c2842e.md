## 一、多级缓存全量统一 (D-182~D-184)

### D-182: Java 8服务接入 ep-cache
8个有Redis但未接入ep-cache的Java服务，统一添加ep-cache依赖+关键热点数据getOrLoad缓存：

| 服务 | 缓存目标 | TTL |
|------|---------|-----|
| core-business | Course列表/详情, User信息 | 300s/600s |
| grading-service | Assignment模板, Submission状态 | 600s/60s |
| portal-bff | API聚合结果, 用户菜单 | 120s |
| boardgame-service | GameRoom状态, GameReplay | 60s/600s |
| senior-care | ElderProfile, CarePlan | 600s |
| order-platform | Order详情(读多写少) | 300s |
| payment-platform | PaymentEntity(只读) | 120s |
| knowledge-platform/knowledge-service | Knowledge文档元数据 | 600s |

**每个服务：** pom.xml加ep-cache依赖 + application.yml加`ep.cache.enabled: true` + 在Service层注入CacheService + getOrLoad包裹热点查询 + evict在写操作后调用 + 单元测试(Mockito mock CacheService)

### D-183: Go ep-go-common 统一cache模块
在`services/ep-common-go/cache/`新建统一cache包，对齐ep-cache语义：
- `CacheService` struct: L1(LRU+TTL, hashicorp/golang-lru或container/list) + L2(go-redis) + Pub/Sub广播
- `GetOrLoad(ctx, cacheName, key, loader, ttlSec, cacheEmpty)` — 与Java同名同语义
- `Put(ctx, cacheName, key, value, ttlSec)` / `Evict(ctx, cacheName, key)` — Evict补Redis Pub/Sub广播(修复当前缺失的正确性bug)
- `EmptySentinel = "__EP_CACHE_EMPTY__"` — 与Java一致
- Pub/Sub channel `ep:cache:invalidate` — 与Java一致，跨语言互通
- ws-gateway的`src/cache/cache.go`改为调用ep-go-common/cache，删除手写LRU
- 测试：miniredis测试L1/L2/广播/空值穿透/evict

### D-184: Python ep-python-common 统一cache模块
在`services/ep-python-common/ep_common/cache.py`新建统一cache模块：
- `CacheService` class: L1(functools.lru_cache + TTL dict) + L2(redis-py) + Pub/Sub广播(threading.Thread订阅)
- `get_or_load(cache_name, key, loader, ttl_sec, cache_empty)` / `put` / `evict`
- `EMPTY_SENTINEL = "__EP_CACHE_EMPTY__"` — 与Java/Go一致
- Pub/Sub channel `ep:cache:invalidate` — 三语言互通
- ai-platform的`semantic_cache.py`改为调用ep-python-common cache + 保留语义哈希层
- 测试：fakeredis测试L1/L2/广播/空值/evict

## 二、Firecracker microVM沙箱 (D-185)

### 实现：Java进程级隔离 + judge0队列模拟 + SandboxWarmPool CRD

**设计决策(Iron Law 8 3方案评估)：** A) 真实Firecracker(需K8s CRD+运行时) B) Docker容器隔离(需Docker daemon) C) Java进程级隔离+资源限制+Seccomp-like安全策略。选C(离线环境可用，AOT友好，零外部依赖)。

**新增文件 (grading-service)：**
1. `sandbox/SandboxExecutor.java` — 接口: `ExecutionResult execute(ExecutionRequest)`
2. `sandbox/ProcessSandboxExecutor.java` — Java ProcessBuilder启动子进程，设置CPU/内存/超时限制，隔离临时目录，捕获stdout/stderr，30s超时kill
3. `sandbox/SandboxWarmPool.java` — 预热池：维护N个可用进程描述符(LanguageSpec)，minReady=5，replenish
4. `sandbox/LanguageSpec.java` — enum: JAVA(python3/python/go/gcc命令模板), PYTHON, GO, CPP
5. `sandbox/ExecutionRequest.java` / `ExecutionResult.java` — records
6. `sandbox/judge0/Judge0Queue.java` — Redis BRPOP `judge0:queue` 拉取任务(可用RedisTemplate mock)
7. `sandbox/judge0/Judge0Worker.java` — 消费队列→SandboxExecutor→写结果`judge0:result:{token}`
8. `grading/impl/GradingServiceImpl.java` 修改 — `auto_check`阶段调用SandboxExecutor替代硬编码PASSED
9. K8s CRD: `deploy/k8s/base/sandboxwarmpool-crd.yaml` — SandboxWarmPool CRD定义(供生产K8s环境使用)
10. 测试: ProcessSandboxExecutorTest(执行简单echo/超时/异常), Judge0QueueTest(mock Redis)
